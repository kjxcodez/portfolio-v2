I've always been fascinated by how programming languages work under the hood. After years of writing code in Python, JavaScript, and TypeScript, I decided to answer the question I kept putting off: *how hard is it to actually build one?*

The answer: harder than I thought, more rewarding than I expected.

## What is Rune Lang?

Rune is a minimal, dynamically-typed, interpreted programming language. It was never meant for production — it's a learning project. But it has a complete pipeline: a hand-written lexer, a recursive-descent parser, an AST, and a tree-walk interpreter. It also has a VS Code extension with syntax highlighting.

Here's what valid Rune code looks like:

```rune
let name = "world"
print("Hello, " + name)

fn add(a, b) {
  return a + b
}

let result = add(3, 4)
print(result)  // 7
```

## Phase 1: The Lexer

The lexer (tokenizer) is the first stage. It takes raw source code as a string and emits a flat list of tokens. Each token has a type and a value.

```python
class TokenType(Enum):
    NUMBER = "NUMBER"
    STRING = "STRING"
    IDENTIFIER = "IDENTIFIER"
    LET = "let"
    FN = "fn"
    RETURN = "return"
    PLUS = "+"
    EQUALS = "="
    LPAREN = "("
    RPAREN = ")"
    # ...

class Token:
    def __init__(self, type: TokenType, value: str, line: int):
        self.type = type
        self.value = value
        self.line = line
```

The lexer walks character by character, matching patterns. Numbers, strings, identifiers, and keywords all have distinct rules. The trickiest part is handling multicharacter tokens like `==`, `!=`, and `<=` without consuming the next character prematurely.

## Phase 2: The Parser

The parser takes the token stream and builds an Abstract Syntax Tree (AST). I used recursive descent — each grammar rule becomes a function.

```python
class Parser:
    def parse_expression(self):
        return self.parse_assignment()

    def parse_assignment(self):
        left = self.parse_equality()
        if self.match(TokenType.EQUALS):
            right = self.parse_assignment()
            return AssignNode(left, right)
        return left

    def parse_equality(self):
        left = self.parse_comparison()
        while self.match(TokenType.EQEQ, TokenType.BANGEQ):
            op = self.previous()
            right = self.parse_comparison()
            left = BinaryNode(left, op, right)
        return left
```

The key insight is that **operator precedence maps directly to call depth**. `parse_equality` calls `parse_comparison`, which calls `parse_addition`, and so on. Lower precedence = higher in the call chain.

## Phase 3: The AST

Each node type is a Python dataclass:

```python
@dataclass
class BinaryNode:
    left: ASTNode
    op: Token
    right: ASTNode

@dataclass
class FunctionDeclaration:
    name: str
    params: list[str]
    body: list[ASTNode]

@dataclass
class CallNode:
    callee: ASTNode
    args: list[ASTNode]
```

The AST is the source of truth for everything downstream — the interpreter walks it, and a future compiler would emit bytecode from it.

## Phase 4: The Interpreter

The interpreter is a tree-walker. It recursively evaluates each AST node:

```python
class Interpreter:
    def evaluate(self, node: ASTNode) -> Any:
        if isinstance(node, NumberLiteral):
            return node.value
        if isinstance(node, BinaryNode):
            left = self.evaluate(node.left)
            right = self.evaluate(node.right)
            return self.apply_op(node.op.type, left, right)
        if isinstance(node, CallNode):
            fn = self.evaluate(node.callee)
            args = [self.evaluate(a) for a in node.args]
            return fn.call(self, args)
        # ...
```

Closures were the hardest part. Every function needs to capture its defining environment, not the calling environment. I solved this by storing an `Environment` snapshot on each `FunctionValue` at definition time.

## The VS Code Extension

Once the language worked in a terminal, I built a VS Code extension to make it usable. The extension provides:

- **Syntax highlighting** via a TextMate grammar (`.tmLanguage.json`)
- **Code snippets** for common patterns
- **Run file** command — executes the current `.rune` file in the integrated terminal

The grammar file is just a JSON/XML blob that maps regex patterns to scope names like `keyword.control.rune` and `string.quoted.double.rune`. VS Code's tokenizer engine handles the rest.

## What I Learned

1. **Recursive descent is surprisingly readable.** Once you internalize the precedence-as-depth pattern, the parser code almost reads like the grammar spec.

2. **Environments (scopes) are the hard part of interpreters.** Getting closures right took me two rewrites.

3. **Error messages matter.** The first version just crashed with a Python traceback. Adding `line` tracking to tokens and surfacing clean errors like `Line 5: undefined variable 'x'` made debugging Rune programs 10x easier.

4. **Building a language makes you a better user of languages.** I understand why JavaScript has `var` hoisting, why Python chose significant whitespace, and why Rust's borrow checker is designed the way it is — all of it makes more sense now.

The source code is on GitHub. If you want to build your own language, start with *Crafting Interpreters* by Robert Nystrom — it's free online and exceptional.
