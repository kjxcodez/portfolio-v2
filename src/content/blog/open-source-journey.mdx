My first open source PR was terrible. Not the code — the approach. I found a repo I liked, spotted a feature I wanted, and opened a massive 800-line PR with zero prior discussion. It sat unreviewed for three weeks, then got a polite "thanks but this doesn't fit our roadmap" close.

That rejection taught me more than the next five merges combined.

Here's what 10 merged PRs actually looks like from the inside.

## PR #1: The Lesson in Scope

**Repo:** a popular React hooks library  
**PR:** Rewrote the internal caching logic (800 lines)  
**Result:** Closed without merge

The maintainer was kind about it. The problem wasn't the code quality — it was that I'd changed the internal contract of a library without discussing it first. The existing caching behavior, however unintuitive, was depended on by thousands of downstream users.

**Lesson:** Before touching internals, open an issue. Ask "would you accept a PR for X?" and wait for a yes.

## PRs #2–4: Finding the Easy Wins

I changed strategy. I started looking for:

- Typos in docs
- Missing TypeScript types
- Failing tests in CI
- Outdated README sections

```bash
# My actual workflow for finding issues
git clone <repo>
cd <repo>
npm install && npm test
# Look for failures, then trace them
```

These got merged fast — sometimes within hours. More importantly, they got me onto maintainers' radars as someone who actually reads the code.

**Lesson:** Small contributions compound. Three doc fixes in the same repo signals you're serious.

## PR #5: The UI Revamp

**Repo:** `mehul-m-prajapati/github_tracker`  
**PR:** Full UI overhaul  
**Result:** Still open (open PRs aren't failures)

I'd been using this tool and found the UI hard to scan. I redesigned it with better hierarchy and opened the PR with screenshots — before and after. The maintainer loved the direction but had feedback on mobile breakpoints.

This was the first PR where I learned to **attach screenshots to the PR description**. Pull requests with visuals get reviewed 3x faster in my experience.

```markdown
## Changes
- Redesigned header with better visual hierarchy
- Added responsive grid for the stats section
- Improved color contrast for accessibility

## Screenshots
| Before | After |
|--------|-------|
| ![before](./before.png) | ![after](./after.png) |
```

**Lesson:** Show, don't tell. A picture is worth a thousand lines of diff.

## PR #6–9: The Percept UI Sprint

Four consecutive merges into my own project (`perceptui/ui`) — the CLI, issue templates, and component scaffolding. Working on your own open source project counts. You're still practicing the discipline of clean commits, good PR descriptions, and atomic changesets.

The discipline I forced on myself:

- **One thing per PR.** A PR that adds the CLI should not also change button styles.
- **Conventional commits.** `feat(cli): add project creation command` is searchable. `fix stuff` is not.
- **Self-review before opening.** I read my own diffs like a reviewer before marking PRs ready.

## PR #10: First External Merge

**Repo:** `perceptui/vite-react-ts-tailwind-template`  
**PR:** Initialize the template project  
**Result:** Merged

This was the one that felt real. Someone else's project, someone else merging my code. The commit is permanently in that repo's history.

What made it work:
1. I'd discussed the template format in an issue first
2. The PR was focused — exactly what we'd agreed on, nothing extra
3. I included a `README.md` with setup instructions

## The Habits That Actually Matter

After 10 merges, the technical skill matters less than I expected. What matters more:

**Communication over code.** Every rejected PR I've seen fails because of a mismatch in expectations, not because the code was bad.

**Read the CONTRIBUTING guide.** It exists for a reason. Maintainers wrote it because someone didn't do something they needed.

**Be patient.** Most maintainers are doing this in their spare time. A week without a response isn't rejection — it's Tuesday.

**Write the PR description for a stranger.** Not for yourself, not for the maintainer — for someone who has never seen this codebase. If that person can understand what your PR does and why, you've written a good description.

---

I'm at 61 contributions now. The first 10 were the hardest — mostly because I didn't know what I was doing. If you're reading this and wondering whether to start: open the issue. The worst that happens is silence.
